# 全天训练方案 — Episode 延长计划

## 背景

当前训练每个 episode 覆盖 **30-70 分钟** 的市场数据（`NUM_STEPS=64` × `n_data_msg_per_step=120` ≈ 7680 条消息）。这带来了三个问题：

1. **库存积累不足** — 30 分钟内库存变化有限，`InventoryPnL` ≈ 0
2. **T+1 约束形同虚设** — 没有跨日持仓，隔夜惩罚只算了个寂寞
3. **reward 差异小** — GRPO 的 group advantage 基于短时间内的微小差异，信噪比低

将 episode 拉长到 **一整个交易日**（5.5 小时），可以让环境更接近真实做市场景。

---

## 一、改动方案

### 配置改动

当前训练脚本 `GRPO_ippo_rnn_JAXMARL_pmap.py` 和 `ippo_rnn_JAXMARL_pmap.py` 中，episode 长度由两个参数控制：

```yaml
# 当前
NUM_STEPS: 64
world_config:
  episode_time: 64
  n_data_msg_per_step: 120
  start_resolution: 64
```

全天方案（300059 每天约 35825 条消息）：

```yaml
# 全天版本
NUM_ENVS: 4096         # 从 16384 降到 4096（显存考虑）
NUM_STEPS: 300         # 从 64 拉长到 300
world_config:
  episode_time: 300
  n_data_msg_per_step: 120
  start_resolution: 64
```

**改动原理**：
- `NUM_STEPS=300` 每个环境覆盖 300×120=36000 条消息 ≈ 一整天交易
- `NUM_ENVS=4096` 减少并行环境数以腾出显存给更长的轨迹缓冲区
- 总样本量 `NUM_ENVS × NUM_STEPS` 从 16384×64≈1M 变为 4096×300≈1.2M，**基本不变**

### 代码改动

**无需改动。** episode 长度由配置文件控制，数据加载器 `LoadLOBSTER_resample` 的 `_get_inits_day` 函数自动根据 `episode_time` 和 `n_data_msg_per_step` 计算窗口。

## 二、硬件考虑

### 当前硬件

| GPU | 显存 | 数量 | 当前占用（NUM_STEPS=64） | 空闲 |
|:----|:-----|:-----|:------------------------|:-----|
| RTX 3090 | 24GB | 4 | ~22.5GB | ~1.5GB |

### 延长后显存估算

轨迹缓冲区大小跟 `NUM_STEPS` 成正比：

| 参数 | 缓冲区大小/卡 | 预计总占用/卡 |
|:-----|:------------|:------------|
| NUM_STEPS=64, NUM_ENVS=16384 | ~0.4GB | ~22.5GB（当前） |
| **NUM_STEPS=300, NUM_ENVS=4096** | **~0.5GB** | **~18-20GB** ✅ |

**4×RTX 3090 完全够用。** 虽然单条轨迹变长，但 NUM_ENVS 减少到 4096，每卡处理的 actor 数从 40960 降到 10240，总内存需求反而略低。

### 如果需要更大规模

如果希望保持 `NUM_ENVS=16384` 同时拉长 episode，需要更大显存的显卡：

| 显卡 | 显存 | 能否 16384+300 步 | 估算价格 |
|:----|:-----|:-----------------|:--------|
| RTX 3090 | 24GB | ❌ 爆显存 | 已有 |
| RTX 4090 | 24GB | ❌ 同上 | ~1.5万/卡 |
| **RTX 6000 Ada** | **48GB** | ✅ 够 | ~3万/卡 |
| A100 80GB | 80GB | ✅ 宽松 | 租约 $3-5/h |
| RTX 5090（未发布） | 32-48GB? | 可能够 | 未知 |

**建议：先用 4×3090 跑 `NUM_ENVS=4096` 版本验证效果，确认有效后再考虑升级硬件。**

## 三、预期收益

| 收益 | 原因 | 信心 |
|:-----|:-----|:-----|
| **T+1 约束真正生效** | 全天持仓积累，隔夜惩罚开始起实质性作用 | 高 |
| **库存惩罚信号变强** | `InventoryPnL` 在全天价格波动下有实际量级 | 高 |
| **reward 信噪比提高** | 全天累计 reward 差异更大，group advantage 更稳定 | 中 |
| **PPO critic 更好学** | 更长序列让 value function 看到更多状态 | 中 |
| **策略更贴近实盘** | 全天做市 vs 30 分钟迷你做市 | 确定 |

## 四、代价与风险

| 代价 | 严重度 | 说明 |
|:-----|:-------|:-----|
| NUM_ENVS 减到 4096 | 🟡 中 | 每个 batch 的样本多样性下降，可能影响泛化 |
| 每步训练时间略长 | 🟢 低 | 轨迹更长，但 actor 数更少，吞吐量相近 |
| 每局训练次数减少 | 🟡 中 | 全天模式下 57 天数据只能切 ~57 局（原来约 228 局） |
| 环境重置频率降低 | 🟢 低 | 对训练影响不大 |

**最大的风险**是 `NUM_ENVS=4096` 导致 batch 太小，策略更新不稳定。如果出现这种情况，可以尝试：

1. 增大 `NUM_MINIBATCHES`（从 32 降到 8，让每个 batch 更大）
2. 降低 `UPDATE_EPOCHS`（从 4 降到 2，减少过拟合风险）

## 五、与现有成果的关系

当前 PPO + spooner 已跑出 **MM=+0.00034, EXE=-0.037** 的历史最佳结果。全天方案在这个基础上：

```
当前（30-70分）:    PPO + spooner → MM 正收益 ✅  （已跑通）
下一步:            PPO + tplus1 → 是否正收益？  （正在跑）
再下一步:          全天 episode + PPO → 更真实   （本方案）
```

**全天方案应该等 PPO + tplus1 的结果再决定是否启动** — 如果加回成本后净利已经为正，那就不需要改；如果还是负，全天方案的更强信号可能帮助 PPO 跨过成本门槛。

## 六、后续改进方向

1. **阶梯式拉长** — 先试 `NUM_STEPS=128`（2小时），再试 256（4小时），最后 300（全天），逐步找最佳点
2. **降低 NUM_MINIBATCHES** — 从 32 降到 16 或 8，补偿 NUM_ENVS 减少带来的 batch 多样性损失
3. **增大 LR 或降低 KL_COEF** — 更长 episode 意味着更少的更新步数，可能需要更大步长
4. **多个全天 episode** — 如果显存允许，把 57 天的 57 局串联成更长的训练序列
5. **动态 NUM_ENVS** — 起步用 4096 跑全天，如果效果验证了，再买更大显存卡恢复到 16384
